# Git Workflow

各ルールは「Yes/No で判定できる条件」として記述しています。

---

## ブランチ運用

- `main` / `master` への直接プッシュをしていないか？→ Yes（直接プッシュしている）なら feature ブランチを使う
- ブランチ名は以下のプレフィックスを持つか？

  | プレフィックス | 用途 |
  |---|---|
  | `feature/` | 新機能 |
  | `fix/` | バグ修正 |
  | `docs/` | ドキュメント |
  | `chore/` | 設定・依存更新 |
  | `refactor/` | リファクタリング |

## コミットメッセージ

- 1コミット1変更の原則を守っているか？
- メッセージは `<type>: <subject>` の形式か？
  - 良い例：`fix: ログイン時のnullチェックを追加`
  - 悪い例：`fix`、`update`、`wip`
- `subject` は動詞で始まっているか？（例：「〜を追加」「〜を修正」）

## コミット前チェック

- 不要なデバッグコード（`console.log` 等）を削除したか？
- `.env` や秘密情報を含むファイルをステージングしていないか？
- テストが全てパスするか？→ No なら修正してからコミットする
- `git diff --staged` でセルフレビューをしたか？

## PR / レビュー

- PR の説明に「何を・なぜ変更したか」が記載されているか？
- PR のサイズは500行以内か？→ No なら分割を検討する
- レビュワーが理解できるレベルのコンテキストが書かれているか？

## 禁止事項

| 禁止 | 理由 |
|---|---|
| `git push --force` を `main` に対して実行する | 他者のコミットを消す可能性がある |
| `--no-verify` でフックをスキップする | CI/品質チェックを意図的に回避することになる |
| コミットメッセージを曖昧な単語だけにする（`fix`、`update` など） | 変更の意図が追跡できなくなる |
| マージコミットなしで force push で履歴を書き換える | 公開済みのコミットを変更してはいけない |
