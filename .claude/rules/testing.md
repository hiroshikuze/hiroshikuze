# テスト方針

各ルールは「Yes/No で判定できる条件」として記述しています。

---

## テスト作成判断

- 新機能を追加したか？→ Yes なら単体テストを書く
- バグを修正したか？→ Yes なら再現テストを書いてから修正する
- 既存テストが全てパスするか？→ No なら修正前に原因を調査する
- パブリック API を変更したか？→ Yes なら統合テストも更新する

## テストの品質

- テスト名は「何をテストしているか」が一読で分かるか？
  - 良い例：`test_login_with_invalid_password_returns_401`
  - 悪い例：`test_login_error`
- 1テスト1アサーションの原則を守っているか？（関連するアサーションのグループは許容）
- モックは必要最小限か？（過剰なモックはテストの信頼性を下げる）
- テストは独立して実行できるか？（他テストの実行順に依存していないか）

## カバレッジ

以下の3パスを網羅しているか？

| パス | 内容 | 例 |
|---|---|---|
| ハッピーパス | 正常系 | 正しい入力で期待通りの出力 |
| エッジケース | 境界値・特殊入力 | 空文字・null・最大値・最小値 |
| エラーパス | 異常系 | 例外・エラーレスポンス・タイムアウト |

## 禁止事項

| 禁止 | 代替 |
|---|---|
| テストのためだけにプロダクションコードを変更する | テスタブルな設計に最初からする |
| `sleep` / `timeout` で非同期処理を待つ | モックや `waitFor` を使う |
| テストデータをベタ書き（ハードコード） | フィクスチャ・ファクトリを使う |
| テストをコメントアウトして放置する | 削除するか `skip` を使い理由を明記する |
