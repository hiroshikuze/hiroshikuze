# コーディング規約

各ルールは「Yes/No で判定できる条件」として記述しています。

---

## 関数・クラス設計

- 関数は50行以内か？→ No なら分割する
- 1関数1責務か？→ No なら分割する
- 副作用のある関数は `save`, `send`, `update`, `delete` などの明示的な名前か？→ No なら改名する
- クラスは単一の概念を表しているか？→ No なら分割を検討する

## import 順序

外部ライブラリ → 内部モジュール → 型定義 の順になっているか？

```ts
// 外部ライブラリ
import React from 'react'
import axios from 'axios'

// 内部モジュール
import { UserService } from '@/services/user'

// 型定義
import type { User } from '@/types'
```

- 各グループ間に空行があるか？→ No なら追加する

## 命名規則

- 変数・関数は camelCase（JS/TS）または snake_case（Python）か？
- ブール値は `is`, `has`, `can`, `should` で始まるか？
- 定数は `ALL_CAPS` か？
- 略語は避け、意図が伝わる名前か？（例：`u` → `user`、`tmp` → `tempFile`）

## コメント

- 自明でないロジックにのみコメントを書いているか？（自明なコードにコメント不要）
- 「何をしているか」ではなく「なぜそうするか」を説明しているか？
- TODO コメントは `// TODO(name): 内容` の形式か？

## セキュリティ

- ユーザー入力を直接 SQL・シェルコマンドに渡していないか？→ プレースホルダを使う
- XSS 対策（出力エスケープ）を施しているか？
- シークレット情報（APIキー、パスワード）をハードコードしていないか？→ 環境変数を使う
- 依存パッケージのバージョンを固定しているか？

## 禁止事項

| 禁止 | 代替 |
|---|---|
| `any` 型（TypeScript） | 具体的な型・`unknown` を定義する |
| `console.log` を本番コードに残す | デバッグ後は削除またはロガーに置き換える |
| マジックナンバーの直接使用（例：`* 86400`） | 定数として定義する（例：`SECONDS_PER_DAY`） |
| ネストが4段以上の条件分岐 | 早期 return・関数分割で平坦化する |
